# Reports (NIP-56) are a fifth accepted guest kind, bridged into the relay from both entry points

ADR 0006 let a visitor write a narrow set of interaction kinds into the owner's videos: comments, replies, reactions, and deletion of their own accepted interactions. Reporting was out of scope. The site now gets one report action and the owner gets one place to review it, so reports join that same narrow inbox instead of opening a second, unrelated moderation surface.

**Acceptance rule.** Kind 1984 (NIP-56) is accepted under the same resolution rule as ADR 0006: every `e`, `p`, `x` or `a` tag on the event must resolve against locally stored data — `e` to a locally known video or a comment/reply on one, `a` (when present) to that same video's own coordinate, `p` to the exact author of the `e` target (or, with no `e`, to an allowed writer or another visitor who has interacted here), `x` to one of the media hashes of a locally stored video of an allowed writer — this instance's own `imeta`/`url` parsing (`relay.rs`'s `media_hashes`, indexed by the `media_ref` table), not Almond's file index, so the check stays inside the relay and has no Blossom dependency. With an `e` present, `x` is checked against that one video's media; with no `e` (a BUD-09 client that only knows the blob), `x` is looked up directly against the media index, and a matching `p` must then name one of that blob's video authors. A bare `a` with no `e`, by contrast, cannot be resolved without scanning every writer's video and stays refused. An event with none of these, or with a tag that doesn't resolve, is refused — the same way a comment on a foreign video is refused today. This widens ADR 0006's rule in one way: a profile-only or blob-only report (`p` and/or `x`, no `e`) needs no video identity on the event itself, only a locally known account or blob — the first guest interaction that isn't anchored to a specific video reference. NIP-56's own text is inconsistent here (it says `p` MUST be present, but its own blob-report example carries only `x` and `e`), so we don't enforce "`p` always required" ourselves; we require at least one resolvable target tag. ADR 0006's deletion right already covers "the sender's own accepted interactions" generically, not kind by kind, so a reporter can retract their own report the same way a commenter retracts a comment — no change needed there.

**One relay, one handler.** The site's report button publishes one signed kind 1984 event straight to the relay. `PUT /report` (BUD-09) is the one other entry point a generic Blossom client might use — nostube-server, which already owns the dispatch decision for that path (`is_blossom` in `main.rs`), takes it out of Almond's hands entirely: it parses the posted NIP-56 event itself and runs it through the identical relay acceptance path, answering `202` on success, the relay's own refusal as a `4xx`, or `5xx` on an internal error. Almond's `report_access` stays `Off` and unused — no event ever reaches it, so there is no second validator that can drift out of sync with the relay's, and no JSON audit file that nobody reads. Every report, from either entry point, ends up as exactly one kind 1984 event in the relay, so the studio's `ModerationPage` — already a Nostr client — sees all of them with one query.

**No new status storage.** A report counts as handled once its target is already acted on through an existing path: the author or comment is muted, the video is hidden or deleted, the blob is deleted. "Reviewed, no action needed" has no home yet — left open, not decided here.

Reads of kind 1984 stay open to any client, as NIP-56 assumes elsewhere on the network. There is still no spam protection against reports from throwaway keys, the same open gap ADR 0006 already carries.

## Considered Options

- **A server-side reports table plus an admin endpoint merging the relay and Almond's `reports/*.json` files**: rejected. It stores the same signed event twice and still needs its own status column.
- **Let Almond accept the report (`report_access = Public`) and have nostube-server re-submit it into the relay after the fact**: rejected. It needs a response-inspecting wrapper around `/report`, leaves Almond's own JSON audit file as a second, unread copy, and risks the two acceptance rules disagreeing over time. Handling `/report` directly, with `report_access` left at `Off`, is both simpler and the one place the rule is checked.
